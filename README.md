# Billing and Management System (Demo Edition)

A working, data-backed demo of billing, purchasing, stock, payroll and accounts for a small manufacturing and trading business. It uses generic names only (Product A, Customer A, Worker A) and the brand placeholder `[Your Brand Name]`.

The demo runs on Netlify: a React app served from the CDN and a real TypeScript backend (Hono) running as a Netlify Function. There is no external database. Demo data is generated by the backend on first load, and new records are saved to Netlify Blobs.

## Run it locally

Requirements: Node 20 or later and pnpm 9 (`corepack enable` installs it).

```bash
pnpm install
pnpm dev
```

Open http://localhost:5180 and sign in with any login below.

`pnpm dev` starts two things:

- the API on http://localhost:8888, the same Hono app the Netlify Function runs, using the in-memory store (data resets when it restarts);
- the web app on http://localhost:5180 (Vite), which forwards `/api` to the API.

To run the real Netlify runtime with the local Blobs sandbox instead, install the Netlify CLI and run `pnpm dev:netlify`.

## Deploy to Netlify

1. Push the repository to GitHub and choose **Add new site → Import an existing project** in Netlify.
2. Netlify reads `netlify.toml`. The build command is `pnpm build`, the publish folder is `apps/web/dist` and the functions folder is `netlify/functions`.
3. Set the environment variables below in **Site configuration → Environment variables**.
4. Deploy. In the deploy log, check that the `api` function lists its rate-limit rule.
5. Open the site, sign in as `admin` and run the demo script. Use a deploy preview for rehearsals. Each deploy context (production, deploy preview, branch) has its own data store, so a preview never touches production demo data.

## Environment variables

| Name | Required | Value |
|---|---|---|
| `JWT_SECRET` | Yes | A long random string. Signs session cookies. Never commit it. |
| `DATA_STORE` | No | `blobs` (default on Netlify) or `memory` |
| `DEMO_RESET_ENABLED` | No | `true` (default) allows Admin → Settings → Data tools → Reset demo data |
| `SEED_VERSION` | No | Number stored with the seed. Change it to mark a new seed. |
| `SEED_NOW` | No | Pins the seed date (ISO time). Used by the visual tests only. |

## Resetting the demo data

Sign in as `admin`, open **Settings → Data tools**:

- **Reset demo data** restores the original seed. Everything created since is removed.
- **Export data** downloads all demo data as JSON.
- **Import data** replaces the demo data with an exported file.

The seed is generated by code in `server/src/seed`. It runs the real services over a simulated 60-day history with a fixed random seed, so the data is the same every time and every number reconciles. Dates are relative to the day it is first loaded, so dashboards always look current.

## What is real and what is simulated

| Item | In this demo |
|---|---|
| Backend, sign-in, roles, validation, rate limiting, concurrency control | **Real**, running on Netlify Functions |
| Scaling across instances | **Real**, provided by Netlify serverless and CDN. There is no custom load balancer. The nginx design is shown in Admin → System only as the production target. |
| Database | **None.** Generated seed data plus Netlify Blobs for new records. Blobs is object storage, used here only as the demo's persistence adapter. It is not a production data store. |
| Live updates to Admin | **Real across devices** by polling every 2 seconds, instant between tabs of one browser. Not push (no WebSocket or SSE). |
| PDF | Browser print or **Save as PDF** with the A4 templates. Not rendered on the server. |
| Email | Outbox screen only. Nothing is sent. |
| Security hardening | Good for a demo. Production needs its own review, a real database and secrets management. |

Production adds a real PostgreSQL database, server-rendered PDFs, load-balanced app servers and push updates. The API contract and the business services are kept compatible with that target.

### How the backend stays consistent without a database

- All business data that must change together lives in one versioned JSON document. Every operation reads it, applies the service logic, and writes it back only if nobody else changed it in between (compare-and-set), retrying up to five times. Two workers can never sell the last unit twice.
- The audit log, login history, event feed and request log are kept in separate append-only keys so they never conflict with business writes.
- Creates and payments accept an `Idempotency-Key`; a repeated request returns the first response. Edits of draft bills and indents send `If-Match`; a stale version gets 409.
- Rate limiting has two layers: Netlify's platform rule in the function config, and an app-level limiter (5 sign-in attempts per minute per username, a 15-minute lockout after 10 failures, 120 API requests per minute per user).

## Project layout

```
apps/web            React app: routes, features, design system (ui), API client, A4 print templates
netlify/functions   api.ts (Hono app and its rate-limit config), sweeper.ts (scheduled every 5 minutes)
server/src          routes, middleware, services (business rules and access checks), store, seed, logs
packages/contract   zod schemas, types and the pure calculators (calcInvoice, calcPayslip, calcSettlement)
tests               unit, api, e2e
scripts             dev runner, seed verifier, load test, palette check
docs                the specification, and screens/ with screenshots from the last e2e run
```

## Demo script

The full 23-step walk-through is in `docs/11-testing-and-demo-script.md`, Section 14. Useful places for the engineering steps:

- **Admin → System → Request log**: every API call with status, latency, request id and the function instance that served it.
- **Admin → System → API explorer**: the OpenAPI document generated from the zod schemas.
- **Admin → System → Engineering demos**: one-click demos of the 429 limiter, idempotent replay, the 409 edit conflict and the last-unit race.
- **Admin → System → Architecture**: the running demo design and the labelled production target.
- **Settings → Rules**: raise the worker login limit; **Workers and logins** shows "3 of 10 worker logins used".
